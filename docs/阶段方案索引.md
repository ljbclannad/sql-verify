# SQL Tool 总体架构与阶段设计索引

文档类型：设计文档。

本文与三个阶段文档共同定义 SQL Tool 的目标、职责边界、数据流和关键设计约束。阶段编号用于组织能力设计，不表示运行顺序或开发排期。设计约定不作为实现完成或数据库兼容性通过的证明；具体支持范围与使用方式见各工具说明。

## 1. 总体目标与职责划分

目标是为数据库迁移与替换提供可追溯的 SQL 核查链路：收集业务 SQL，形成固定验证输入，在明确的数据与结果范围内比较双库行为。

| 设计阶段 | 核心职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| 阶段一：SQL 提取 | 发现定义，整理模板、有限条件结构与诊断 | 业务项目与提取配置 | 提取清单、源码线索与提取诊断 |
| 阶段二：双库验证 | 固定输入的双侧执行、结果比较与写入恢复检查 | 独立查询清单或受控 DML 用例、验证配置 | 执行证据、比较结论与恢复报告 |
| 阶段三：清单生成与覆盖 | 补充参数依据，选择代表性场景并生成独立执行清单 | 提取结果、明确参数或单源只读采样、补充资料 | 查询清单、受控 DML 用例与覆盖诊断 |

## 2. 数据流与组件关系

```text
业务项目 → 阶段一：SQL 提取 → 提取结果
                                  ↓
显式参数／单源只读采样 → 阶段三：清单生成
                                  ↓
                          查询清单／DML 用例
                                  ↓
手工或其他工具生成的清单 → 阶段二：双库验证
                                  ↓
                         执行、比较与恢复报告
```

统一入口按“提取 → 生成 → 验证”衔接本轮文件，各工具保留独立入口。入口负责阶段调度与产物传递，各组件负责自身的输入检查和业务规则；入口默认数据基线一致，不自动开启写入验证。

`sql.json` 保存定义、来源、模板和提取诊断；`queries.json` 与 `dml-cases.json` 保存固定执行输入；`coverage.json` 保存生成依据与缺口。提取结果与执行清单分别承担梳理和执行职责，展示 SQL 不能代替完整的 SQL 与有序参数。

## 3. 依赖边界

`sql-query-contract` 定义查询及 DML 模型、读取与格式校验；提取器、生成器和验证器分别承担提取、生成和执行职责。

```text
sql-extractor ───────────→ sql-query-contract
sql-manifest-generator ──→ sql-query-contract
sql-verifier ────────────→ sql-query-contract
```

图中箭头表示工程依赖，区别于第二节的文件流。生成器与提取器、验证器同属根工程子模块，通过项目依赖复用契约模型与校验，不依赖提取器或验证器的实现 JAR。契约模块不依赖业务 classpath、MyBatis、Spring 或数据库驱动。

数据库采样、模板求值、参数转换、去重与清单写出归属生成器；验证器只消费固定输入，不加载业务 Mapper、DTO 或插件，不重新采样或展开条件。生成器按契约编码写出清单，再使用契约读取器核对格式和条目一致性。

根工程统一管理全部子模块的构建与检查，Gradle 根据项目依赖自动构建契约模块。工作区检查还覆盖本地组件衔接；构建与检查不自动开展业务数据库验证。

源码运行产物归属根工程或对应模块的 `build/`，独立运行包的产物归属包内 `reports/`；人工编写的报告示例与真实运行结果分别管理，运行结果不进入源码示例或交付包。

配置与示例按组件职责维护：提取、验证和统一流程配置在根 `config/` 下分类，生成器综合示例在根目录 `config/generator/` 与 `examples/generator/` 维护，专题与运行包示例保留在生成器模块内。统一流程引用组件配置，交付包从所属来源生成，不维护手工副本；分类与路径约定见[配置与示例归属](../config/README.md)。

组件内部按输入、参数、模板、采样、执行和报告等职责组织代码；各组件保留自身配置校验与错误处理，共享契约继续保持独立。模块职责及使用入口见[模块说明](../README.md#模块与进一步使用)，内部分组不改变工程依赖、阶段顺序或文件接口。

## 4. 关键设计决策

| 决策 | 目的与约束 |
| --- | --- |
| 查询清单保持最小输入 | 每条仅保存 id、sql 和可选 parameters，来源诊断与执行配置分别管理 |
| 双侧复用同一输入 | SQL 和类型化有序参数在生成时固定，执行时不重新产生样例值 |
| 场景与参数一一对应 | 每个生成场景固定自身 SQL、参数及断言，保留 foreach/bind 附加参数依据 |
| 业务转换归属清单生产侧 | 必须有可靠类型与转换依据；无法恢复的业务转换形成缺口，验证器不猜测 |
| 直接比较整行 | 保留值的位置和重复次数，列名及 JDBC 列类型不作独立核验 |
| 结果读取范围单独判定 | rows 控制保存行数并额外探测一行，区分完整、分页、前缀和不确定范围 |
| 数据基线默认一致 | 使用工具时默认两库数据已对齐，不设置额外确认开关；工具不执行同步或基线核验 |
| 查询与 DML 分批 | 查询可并发；DML 串行、逐侧独立事务、显式回查、无条件回滚及恢复检查 |
| 人工预算作为正常截断 | 保留数量、截断及未观察证据；参数、采样、SQL 等真实错误继续影响 PARTIAL |
| 各类结论分别记录 | 提取、生成、执行、比较与恢复分别判断，局部成功不能推导整轮通过 |

结果一致性要求数据基线、取数范围与执行条件能够确认。提取成功不等于执行成功，两侧执行成功不等于数据一致，限定范围内一致不等于完整数据集一致。

## 5. 目标环境与能力边界

| 项目 | 设计目标环境 |
| --- | --- |
| 源数据库 | MySQL 8.0.x |
| 目标数据库 | YashanDB Enterprise Edition Release 23.4.14.100，x86_64 |
| 目标兼容模式 | MySQL 兼容模式 |

目标环境用于界定设计讨论范围，不代表该数据库与驱动组合已经通过验证。实际版本及行为以指定环境的执行证据为依据，协议元数据不能证明原生数据库版本。SQL 提取不需要数据库连接。

本链路覆盖 SQL 梳理、固定输入的 JDBC 查询比较和受控单条 DML 的事务内行为。提交、XA、复杂业务事务、数据同步和正式性能验证属于独立范围。运行 SQL 捕获及 Mapper/API 返回映射作为扩展设计，不能计入现有静态提取与清单验证的覆盖结论。
