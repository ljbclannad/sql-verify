# 阶段一：SQL 提取与工程接入设计

文档类型：设计文档。

导航：[总体设计索引](./阶段方案索引.md) · 相关设计：[双库执行与比较](./阶段二-双库查询执行与对比方案.md) · [清单生成与覆盖](./阶段三-场景与运行覆盖规划.md)

本文定义 SQL 提取阶段的职责、输入输出、参数规则及接入约束，不记录开发进度或运行步骤。具体配置与操作见[提取器使用说明](../sql-extractor/README.md)。

## 1. 目标与范围

围绕 MySQL 迁移到 YashanDB 的验证目标，建立可追溯的 SQL 清单，收集模板、保留 `?` 的参数化 SQL、条件组合及提取诊断。扫描范围同时保留增删改查定义，供生成阶段按命令类型选择场景。

提取职责归属 `sql-extractor`，与清单生成及双库验证解耦。根据来源按需读取源码、XML，加载 Mapper、参数类型及扩展类，无需启动完整 Spring 应用。业务差异通过外部配置与运行 classpath 接入，核心流程不包含业务专属包名或目录。

本阶段不连接数据库、不执行 SQL、不加载完整业务插件链，也不验证数据库方言、性能或查询结果。明确接入的业务表名适配器可以复用离线可调用的表名处理代码。提取清单是迁移验证的输入，提取成功不能直接等同于两库兼容。

## 2. 提取来源与处理边界

| 来源 | 设计职责与边界 |
| --- | --- |
| XML | 收集 CRUD、引用片段、跨 namespace 依赖、`databaseId` 变体与 `selectKey`；尝试注册和拼装参数化 SQL |
| Mapper 注解 | 收集注解 SQL，并由 MyBatis 生成参数化结果 |
| Provider | 调用可加载的 Provider 生成 SQL，失败跳过并记录原因 |
| MyBatis-Plus | 收集默认 CRUD 和配置的自定义注入器 SQL；Wrapper 查询及受限更新使用可恢复的业务源码调用结构 |
| Java 源码 | 静态扫描 SQL 字符串、构造器和 Wrapper 原文，记录源码位置；动态片段不保证还原成完整运行 SQL |

扫描范围由来源类别、Mapper 包范围、源码包范围及排除路径共同限定。Java 源码扫描与运行类型扫描分别处理，纯源码分析不要求业务 classpath。

XML 中收集了不同 `databaseId` 的定义，不表示全部变体均已注册并成功生成参数化 SQL。仅导出与当前注册语句匹配且拼装成功的定义；被同名定义或框架选择替代的条目跳过并记录原因。Provider、TypeHandler 注册和参数构造入口可能执行目标项目代码，应接入可信项目；导出不调用 TypeHandler 的 JDBC 参数绑定。

## 3. 条件展开与参数规则

动态 XML 使用 `SAMPLE` 模式，支持常见 `if/choose`、简单 `bind`、集合与字符串条件，`where/set/trim/foreach` 交给 MyBatis 拼装。按参数化 SQL 结构去重，每个定义的 `max-combinations` 默认 256。

展开针对有限候选参数域。复杂 OGNL、任意集合长度、跨参数计算、动态表名与任意 SQL 片段不能承诺穷尽。`combinationsComplete` 及警告描述本轮候选域的处理情况，不是业务全部路径的覆盖证明。

提取器不接受业务参数文件及单条覆盖；参数配置、类型化绑定及采样归属生成器。提取器仅使用内部样例完成有限结构求值，并统一记录 `parameterMode: "SAMPLE"`。生成器不再提供历史 `CONFIGURED` 参数基准的兼容处理。

内部样例不填入导出 SQL。`sql`、`parameterizedSql` 及变体均保留 `?`，不进行离线 JDBC 参数绑定。原 SQL 的常量、引号和注释保持原样。

在固定表名适配之后，为语法树确认的未引用 MySQL 8.0 保留字表名、字段名补反引号，并同步到模板、顶层结果和全部条件变体，避免生成器重新求值时恢复未引用标识符。例如字段 `key` 改为 `` `key` ``，参数路径 `#{key}` 和动态条件属性不变。XML 先投影为 SQL 定位标识符，不能整体解析时按文本节点补齐常见条件、赋值及查询上下文；已有引号、字符串、注释、函数调用与语法关键字保留。不改写非保留字、别名、Java 静态源码片段，以及解析器无法识别的 SQL 或不完整片段；此处理不承担方言转换或数据库验证。

Wrapper 自动场景不构造携带示例实体的查询条件，避免简单字段填值及 getter 默认值误触发实体等值过滤。提供源码时，以明确的 Mapper 调用及方法内顺序数据流为依据，使用已注册实体元数据恢复受支持的 Wrapper 操作；简单本类转发只追踪一层，不执行任意业务表达式。更新支持明确的 set/eq 源码结构，业务值由生成器准备。

源码场景按原 Mapper 定义输出到 `variants`，`wrapperStrategy` 区分 `SOURCE` 和 `EMPTY_FALLBACK`，`wrapperSources` 记录文件、行号、方法及变体索引。值位置和集合代表长度只用于结构恢复，不等同真实参数。未支持的条件开关、控制流、原始片段及跨方法状态保留缺口；已识别调用全部失败时跳过定义。无关联调用只允许查询保留空 Wrapper 基线；Wrapper 更新必须有可恢复的赋值及条件；Wrapper 删除跳过，不生成无条件 SQL。详细支持范围见 [Wrapper 查询恢复说明](../sql-extractor/README.md#wrapper-查询如何恢复)。

## 4. 工程接入设计

提取器需要可信且完整的类型、资源和依赖信息时，以业务运行 classpath 为接入边界；不同准备方式汇入同一提取流程，不要求业务项目修改源码或构建配置。

| 接入方式 | 设计职责与前提 |
| --- | --- |
| 自动 Gradle 接入 | 配置 `project-root`；`module` 默认 `:`。目标须有 Wrapper，模块应用 Java 插件；工具调用目标构建，按需编译并导出运行时 classpath |
| 手工 classpath | 使用 `classpath` 数组、`classpath-file` 或两者合并，提供实际存在的类目录、资源目录和依赖 JAR |
| 纯 Java 源码 | 使用 `sources: "java"` 与源码目录，无需业务 classpath，不调用目标构建 |

显式 classpath 优先于自动准备。自动接入逐轮取得运行 classpath，构建失败停止提取，不复用历史清单，以避免使用过期类与资源。目标构建可能更新其输出与缓存，但接入流程不改写源码或构建配置。

业务表名适配通过运行 classpath 的 `ServiceLoader` 扩展自动发现，按定义身份限定作用域。适配器复用业务现有表名处理器，不要求调用方维护逐表映射，也不在通用流程中写死业务类型或前缀规则。固定表引用在模板、顶层参数化 SQL 和全部变体中同步改写；XML 标签、参数占位符、SQL 字符串与注释保留。输出记录实际映射及原模板指纹，改写失败撤销执行结果并跳过该定义，原因写入跳过记录和全局错误清单。

AIMB 适配实现取得业务动态表名处理器，但不启动 Spring 或调用数据库工厂。日志相关类、日志表及年度分表暂不作为兼容性验证输入，包含日志表的查询和写入整条排除，不枚举年份；明确的源码日志片段也排除。范围排除保存独立证据，不混入执行成功或覆盖完成结论。未匹配该适配器的其他项目保持自身提取行为。

路径按所属配置或清单的目录解析，避免依赖业务项目固定目录。类目录、资源目录和依赖 JAR 分别表达；目录通配仅匹配直接包含的 JAR，不递归推导类目录。Spring Boot 嵌套可执行 JAR 不视为普通 classpath。具体路径及覆盖配置见项目使用说明。

## 5. 输出与状态设计

每轮输出使用独立目录，保留以下职责不同的产物：

- `all.sql`：模板、参数化 SQL 和源码片段，不能整份执行。
- `sql.json`：成功提取的定义、状态、参数模式、条件变体和警告。
- `sql/`：按来源和 Mapper 分类的 SQL 文件。
- `java-sql.sql/json`：源码提取结果及位置。
- `errors.json`：类加载、XML 解析、Mapper 注册等错误。
- `exclusions.json`：范围排除或未成功提取而跳过的定义、源码片段身份及原因，不保存失败 SQL 模板。

`sql.json` 及按 Mapper 分类的 SQL 只保留 `FILLED` 且具有非空参数化结果的定义。`FILLED` 沿用历史状态名，表示至少生成并校验一条参数化 SQL，不表示已填入参数值；`TEMPLATE` 和 `UNRESOLVED` 仅用于内部失败诊断及跳过记录。动态占位符无法确定、参数构造失败、未注册或表名改写失败的定义直接跳过，保留身份和原因，不输出失败模板。已生成有效 SQL 的定义即使存在组合警告或展开上限提示仍保留。Java 静态源码片段保持独立输出。跳过原因、组合警告与全局错误分别保存，`errors.json` 为空不表示全部定义都成功提取。

提取输出用于审阅及生成阶段的输入，不约定包含供双库重放的完整有序参数与绑定快照。定义身份、来源与模板保留原有关系，生成器不能把变体序号当作参数依据。

## 6. 阶段衔接与扩展边界

提取结果通过[阶段三生成器](./阶段三-场景与运行覆盖规划.md)补齐参数依据、选择场景并产生执行清单，再交给[阶段二验证器](./阶段二-双库查询执行与对比方案.md)。执行清单与提取诊断分别管理，验证器无需业务类或 MyBatis。该链路不以提取器直接导出 `queries.json` 为前提。

运行期 Wrapper、需要真实上下文的动态表名，以及分页等其他插件改写仍属于运行 SQL 捕获的扩展设计。已接入的固定表名适配只证明本轮应用了指定业务处理规则；Mapper/API 返回映射属于应用层覆盖，不由离线提取结论推导。
