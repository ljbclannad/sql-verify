# 统一流程使用说明

`scripts/sql-pipeline.py` 将提取、清单生成和双库验证串联为一轮执行，自动构建工具、传递本轮文件并汇总状态。适合业务源码有变化、需要重新提取并核对数据库的场景。

需要 Python 3.9 或以上、JDK 17，以及已准备好的提取、生成和验证配置。首次接入可直接按[项目 README 的完整示例](../README.md#从业务项目运行完整流程)准备；本文集中说明流程控制和故障处理。

## 启动和配置

在仓库根目录运行：

```bash
python3 scripts/sql-pipeline.py --config config/local/pipeline.json
```

依赖已缓存时可加 `--offline`。工具构建及业务工程自动编译会更新构建产物和缓存，不改写源码。

下面是完整的查询流程配置，组件文件与它放在同一目录：

```json
{
  "extractorConfig": "extraction.json",
  "generatorConfig": "generation.json",
  "queryVerificationConfig": "verification.json",
  "output": "../../build/sql-pipeline",
  "partialPolicy": "stop"
}
```

| 字段 | 要求与作用 |
| --- | --- |
| `extractorConfig` | 必填，指定业务项目和提取范围 |
| `generatorConfig` | 必填，指定参数、采样源库及允许表 |
| `queryVerificationConfig` | 查询验证配置；与 DML 配置至少提供一个 |
| `dmlVerificationConfig` | 可选，明确开启受控写入验证；需串行、表白名单和完整用例 |
| `output` | 默认仓库的 `build/sql-pipeline`，每轮新建目录 |
| `partialPolicy` | `stop` 或 `continue`，默认遇到生成缺口就停止 |
| `driverClasspath` | 可选，额外驱动 JAR 路径数组，同时加入生成器与验证器进程 |

命令的 `--config` 相对于当前工作目录；统一配置引用的文件相对于统一配置目录。组件内部路径继续相对于各自原配置目录，classpath 文本中的条目相对于文本文件目录。

## 文件如何衔接

入口使用根工程 Wrapper 构建生成器与验证器的运行目录，契约模块通过 Gradle 项目依赖自动构建。随后为本轮创建配置副本，覆盖以下字段：

| 工具 | 自动填写的字段 |
| --- | --- |
| 提取器 | `output` 指向本轮 `extraction/` |
| 生成器 | `input` 指向本轮提取结果，`output` 指向 `generation/` |
| 查询验证器 | `queries` 指向本轮查询清单，`output` 指向 `query-verification/` |
| DML 验证器 | `dmlCases` 指向本轮写入清单，`output` 指向 `dml-verification/` |

原配置不变。验证模板可省略由入口填写的 `queries/dmlCases`，单独使用前须补齐。入口不选择历史“最新目录”，也不在本轮失败后回退到旧产物。

数据源、表范围、ID 筛选和比较声明保持原配置。采样源库与验证源库需由你配置为同一环境；`queryIds/caseIds` 及比较声明应使用本轮清单的 ID，不能照搬演示 ID。只配置查询验证不会执行 DML，但不改变生成器的输入范围。

## 生成有缺口时怎么办

先看 `generation/<本轮目录>/coverage.json`。`COMPLETE` 表示按本轮规则和预算完成；`PARTIAL` 表示仍有真实缺口，二者均不表示双库验证通过。

| 情况 | 对生成状态的影响 |
| --- | --- |
| 达到人工组合、探索、读取、体积或超时预算，简单用例未达到配额 | 记录截断，不单独导致 `PARTIAL` |
| 缺参数或类型、模板求值失败、非法 SQL、读库失败等 | 记录真实缺口，影响 `PARTIAL` |
| 成功确认源侧为空 | 记录 `SOURCE_EMPTY` 和跳过证据，不交给双库执行 |
| 配置、连接或产物交付失败 | 运行失败，不继续验证 |

`maxXmlScenariosPerStatement` 控制每定义最终有效组合数，默认 10；`maxCandidateAttempts` 控制探索次数，默认 2048。两者在生成配置中设置，不能把数量达到上限理解为所有分支均已覆盖。

`partialPolicy: "stop"` 时，保留有效产物并返回 2，不运行验证。修复缺口后可重跑；若接受已有缺口，可独立验证这轮已交付清单，或改为 `continue` 重跑完整流程。

`continue` 只验证本轮有效清单，最终仍返回 2。重跑会重新提取和采样；源库变化后，不保证新清单与旧轮次相同。

## 结果、执行顺序与退出码

```text
build/sql-pipeline/<本轮目录>/
├── pipeline.json                 总状态、各步退出码和证据路径
├── configs/                      本轮配置副本
├── extraction/<本轮目录>/         提取结果
├── generation/<本轮目录>/         清单、coverage.json、READY
├── query-verification/<本轮目录>/ 查询比较报告
└── dml-verification/<本轮目录>/   写入及恢复报告
```

入口核对生成器退出码、`READY`、清单数量及覆盖状态后才交接。查询在前，DML 在后；任一验证批次返回非零就停止后续批次。空清单记为 `SKIPPED_EMPTY`，未配置的通道不执行。

| 退出码 | 含义 |
| --- | --- |
| `0` | 生成 COMPLETE，至少一个非空批次执行，所有已执行批次通过 |
| `2` | 生成 PARTIAL、验证未通过或无法判定，或全部已配置批次为空 |
| `1` | 配置、构建、运行或产物核对失败 |
| `130` | 用户中断，保留已产生文件，汇总标记 INTERRUPTED |

先查看 `pipeline.json` 判断停在哪一步，再查看该工具的诊断。HTML 报告用于阅读验证结论，不能代替生成覆盖报告；汇总完成也不能说明未执行的 SQL 已通过。

## 常见问题

| 现象 | 检查方向 |
| --- | --- |
| 构建失败，还没开始提取 | 检查根工程 Wrapper、JDK 和模块依赖；契约模块由 Gradle 自动构建 |
| 生成完成但没有验证报告 | 检查 PARTIAL 策略、空清单及是否配置了对应验证通道 |
| 未知查询 ID 或比较声明报错 | 清除旧演示 ID，按本轮清单配置；需要全部执行时用空筛选数组 |
| 切换数据库后仍在旧库采样 | 同时更新生成器 `datasource` 和验证器 `datasources.source` |
| 想复用原清单只验证数据库 | 使用验证器独立入口，统一入口每轮都会重新提取和生成 |

汇总不保存解析后的密码，但配置副本保留外部凭据引用，SQL、参数和报告仍可能包含业务数据。需长期保留的结果应另存到受控目录，避免随构建产物一起清理。
